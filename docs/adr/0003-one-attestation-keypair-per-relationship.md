# 3. One attestation keypair per relationship

Accepted on 2026-10-05.

## Context

A member can hold several relationships at one organisation and at several organisations, and an Astrana instance
chooses which of them to disclose to each Astrana instance that connects to it. How keys map to relationships decides
what one disclosure reveals about the others.

## Decision

Each relationship has its own attestation keypair, generated by the member's Astrana instance, which keeps the private
key and shows the member only the public key to register. A public key is unique across every relationship the
organisation holds, and an attestation answers for the one relationship the key belongs to.

## Consequences

- Disclosure is selective. An Astrana instance holding relationships X and Y with one organisation can offer only X to
  one Astrana instance, only Y to another and both to a third, and presenting one reveals nothing about the others, at
  that organisation or any other. A key carries nothing that links it to the member's other relationships.
- Each public key must be unique across the organisation, because attestation finds a relationship by its public key
  alone. That matters for security, because public keys are not secret. Registering a key already held by another
  relationship answers HTTP 409 - Conflict.
- Uniqueness is a constraint in the schema and a check in the application, so two members racing to register the same
  key get one HTTP 200 - OK and one HTTP 409 - Conflict, never an HTTP 500 - Internal Server Error.
- One key per member, and one key per member per organisation, were rejected because anyone who saw a key could then
  present every relationship behind it, and the member could not choose what to disclose.
