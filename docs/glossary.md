# Glossary

Where a term names a thing in the code, the identifier is given in brackets.

| Term                                        | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Actor (`actor`)                             | The last argument the organisation's tooling passes to the grant, revoke and extend procedures, such as the name of the person or system making the change. The audit log records it. Changes a member makes on the self-service page have none.                                                                                                                                                                                      |
| Application's role                          | The restricted database role the server runs as. It can read and delete relationship rows, update a relationship's key and insert into the audit log. It can also execute two procedures, the member's own revoke and the procedure that deletes audit log entries older than the retention period. It can do nothing else.                                                                                                           |
| Astrana instance                            | A person's own installation of Astrana, the self-hosted, peer-to-peer social networking application. A member's Astrana instance generates their attestation keypairs and proves their relationships to other instances.                                                                                                                                                                                                              |
| Attestation                                 | The organisation's live answer to one question. Is this key on record? If it is, the answer also gives the type, any subtype and the status of the key's relationship. A verifying Astrana instance accepts the relationship only when its status is active. It is a live lookup, not a token or a signature.                                                                                                                         |
| Attestation endpoint (`/api/v1/attest`)     | The anonymous endpoint that answers an attestation. It takes a key and nothing else. If it does not hold the key, or the input is malformed, it answers only `{ "valid": false }`. It refuses a request body over 64 kilobytes with HTTP 413 - Content Too Large.                                                                                                                                                                     |
| Attestation key (`public_key`)              | The public half of the attestation keypair, 32 bytes. The member registers it with the organisation for one relationship, and an Astrana instance presents it when proving that relationship.                                                                                                                                                                                                                                         |
| Attestation keypair                         | The Ed25519 keypair a member's Astrana instance generates for one relationship. The private key never leaves the instance.                                                                                                                                                                                                                                                                                                            |
| Audit log (`audit_log`)                     | The table recording every grant, extension, revocation, removal and key registration or clearing. Each entry holds the member's identifier and, for the organisation's own changes, the actor its tooling passed. Keys and attestation lookups are never written to it. It is append-only, apart from deleting entries older than the organisation's retention period.                                                                |
| Challenge                                   | A fresh random value of at least 32 bytes that the verifying Astrana instance asks the member's Astrana instance to sign. Signing it proves possession of the private key each time, and nothing reusable changes hands.                                                                                                                                                                                                              |
| Clearing a key                              | A member saving an empty value. This removes the key but keeps the grant. The relationship goes back to waiting for a key, and attestation pauses until the member saves a key again.                                                                                                                                                                                                                                                 |
| Contract                                    | The files under `shared/contract` that define the shapes every implementation serves. They are the OpenAPI document, the manifest schema, the relationship types and the attribution. Parity covers the contract and the shared interface.                                                                                                                                                                                            |
| Decision record                             | One of the architecture decision records in `docs/adr`. Each covers one decision that could be reversed on its own, with what was decided, why, what was rejected and what it costs.                                                                                                                                                                                                                                                  |
| Demonstration                               | The stack each implementation ships in its `demo` folder, for trying the server on your own machine. It holds the application with a database, a TLS proxy and a Keycloak in development mode with sample members and relationships. It publishes its ports on every network address of the machine, so other machines on the network can reach it.                                                                                   |
| Expiry (`expires_at`)                       | The date and time a relationship expires, after which its status is `expired`. Only the organisation sets or clears it, with `extend_member_relationship`. A relationship without one never expires.                                                                                                                                                                                                                                  |
| Extending                                   | The organisation's procedure, `extend_member_relationship`, which sets or clears an expiry and lifts a revocation. It is the only way to restore a revoked or expired relationship.                                                                                                                                                                                                                                                   |
| Granting                                    | The organisation creating a relationship, from its own systems, by calling `grant_member_relationship` in the database. A relationship exists before the member has signed in or registered a key.                                                                                                                                                                                                                                    |
| Identity and access management system       | The organisation's own system for signing people in, which members sign in through over OpenID Connect or SAML. The server holds no accounts of its own.                                                                                                                                                                                                                                                                              |
| Identity provider                           | The identity and access management system in its role during sign-in, when it signs the member in and vouches for them to the server over OpenID Connect or SAML.                                                                                                                                                                                                                                                                     |
| Identity system                             | The short name for the identity and access management system.                                                                                                                                                                                                                                                                                                                                                                         |
| Implementation                              | One of the three servers, built on .NET, Java and PHP, which behave identically on everything the contract and the shared interface define.                                                                                                                                                                                                                                                                                           |
| Landing page                                | The public page at the landing page address, with the organisation's name and logo and a sign-in button. It also answers at `/signed-out` with the sign-out confirmation.                                                                                                                                                                                                                                                             |
| Landing page address (`enrollment_url`)     | Where a prospective member goes to sign in and register a key, normally the server's own root address.                                                                                                                                                                                                                                                                                                                                |
| Language cookie (`ata_locale`)              | The cookie the language switcher sets, holding a locale code and nothing else.                                                                                                                                                                                                                                                                                                                                                        |
| Licence page (`/license`)                   | The page stating the software's licence and trademark notice, rendered from `shared/contract/attribution.json`.                                                                                                                                                                                                                                                                                                                       |
| Live lookup                                 | Checking attestation with the organisation at the moment someone asks. A revocation is seen at the next check, and an unreachable organisation means unknown rather than invalid.                                                                                                                                                                                                                                                     |
| Locale                                      | A language tag such as `fr`, `zh-Hant` or `fr-CA`, as used in `Accept-Language`, the manifest's text fields and the strings file.                                                                                                                                                                                                                                                                                                     |
| Manifest (`/.well-known/ata-manifest.json`) | The public document each server publishes, with its version, the organisation's name, description, logo for light and dark mode, website, support page, privacy notice, jurisdictions, relationship types, default locale, landing page address and attestation endpoint.                                                                                                                                                             |
| Member                                      | A person who signs in through the organisation's identity and access management system to hold relationships, known to the server only by their subject identifier. This is different from the relationship type `member`, which means membership of a club, society or similar body.                                                                                                                                                 |
| Offered locales                             | The locales a server lets a member choose. They are the locales on the organisation's configured list that the strings file also ships, or every shipped locale when the organisation configures none.                                                                                                                                                                                                                                |
| Organisation                                | The party that runs a server and vouches for its own relationships, such as a bank, an employer, a club, a professional body or a government department.                                                                                                                                                                                                                                                                              |
| Organisation's role                         | The database role the organisation's own tooling connects as, which may execute the grant, revoke and extend procedures and nothing else.                                                                                                                                                                                                                                                                                             |
| Parity                                      | The three implementations behaving identically on everything the contract and the shared interface define, so that a member or a verifying Astrana instance cannot tell which implementation answered.                                                                                                                                                                                                                                |
| Registering a key                           | A member saving an attestation key against a relationship on the self-service page. Saving a new key replaces the old one.                                                                                                                                                                                                                                                                                                            |
| Relationship                                | One member's standing of one type with the organisation, held as one row. A member can hold several relationships, each with its own attestation key.                                                                                                                                                                                                                                                                                 |
| Relationship subtype                        | Free text the organisation may set on a relationship, such as a grade or designation. The server does not govern or interpret it.                                                                                                                                                                                                                                                                                                     |
| Relationship type (`relationship_type`)     | A value from the fixed vocabulary in `shared/contract/relationship-types.json`, such as `employee` or `client`, with the same meaning whichever organisation uses it. What each value means is on the [relationship types page](relationship-types.md).                                                                                                                                                                               |
| Removing                                    | A member deleting one of their relationships entirely. Only a new grant brings it back. The audit log records a removal as the event `key_removed`.                                                                                                                                                                                                                                                                                   |
| Revoking                                    | Marking a relationship revoked. The organisation does it with `revoke_member_relationship`. A member can also revoke their own relationship unless it is already revoked, through `member_self_revoke_relationship`, which is the member's own revoke. Either way, only the organisation can undo it.                                                                                                                                 |
| Self-service page (`/me`)                   | The page a signed-in member sees, listing their relationships with the status of each. There they register and clear keys, and revoke and remove relationships.                                                                                                                                                                                                                                                                       |
| Session cookie (`ata_session`)              | The one credential a signed-in member holds, a browser-session cookie that carries identity only.                                                                                                                                                                                                                                                                                                                                     |
| Shared inputs                               | The files under `shared/` that every implementation consumes at build time. They are the contract, the schema files, the interface strings and the stylesheet.                                                                                                                                                                                                                                                                        |
| Shared interface                            | The stylesheet, the strings and the markup the pages share, in `shared/ui`, which every implementation renders the same way.                                                                                                                                                                                                                                                                                                          |
| Sign-in service                             | The PHP installation page's plain name for the identity and access management system.                                                                                                                                                                                                                                                                                                                                                 |
| Standing                                    | What the organisation has granted on a relationship. It is held in the four columns only the organisation writes, which are the type, the subtype, the expiry and the revocation.                                                                                                                                                                                                                                                     |
| Status                                      | What a relationship's standing and key amount to right now. One of waiting for a key (`unkeyed`), `active`, `revoked` or `expired`.                                                                                                                                                                                                                                                                                                   |
| Subject claim                               | The part of a sign-in that carries the subject identifier. By default it is the OpenID Connect `sub` claim or the SAML NameID, and the organisation can configure another claim or attribute instead.                                                                                                                                                                                                                                 |
| Subject identifier (`iam_subject_id`)       | The identifier the organisation's identity and access management system presents for a member at sign-in, as the value of the subject claim. It must be known before the member's first sign-in.                                                                                                                                                                                                                                      |
| Suite                                       | The tests in `shared/test` that define conformance and parity without knowing which implementation they run against. They have three parts, the conformance, differential and accessibility suites. The conformance suite checks one implementation against the contract and the decision records. The differential suite compares the three. The accessibility suite drives the landing page and the self-service page in a browser. |
| Support page (`support_url`)                | The organisation's page for help, whose address the manifest gives.                                                                                                                                                                                                                                                                                                                                                                   |
| Valid (`valid`)                             | The field in an attestation answer that says whether the key is on record. It is `true` for a revoked or expired relationship too, and the status says which. A verifying Astrana instance accepts a relationship only when its status is `active`.                                                                                                                                                                                   |
| Verifying Astrana instance                  | The Astrana instance that checks a peer. The peer shows it a member's key and signs a challenge with the matching private key. The verifying instance then asks the organisation whether the key is on record. The contract and the code sometimes call it the verifying peer.                                                                                                                                                        |
